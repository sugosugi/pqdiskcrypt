# pqfilecrypt / pqdiskcrypt 安全评审与加固说明

> 历史材料：本文件来自原始压缩包，仅保留作背景记录。这里的旧版本结论不构成当前版本的安全审计或保证。当前限制和测试证据以包根目录 README.md 和本目录 verification-results.json 为准。

> **第四轮（八节）把工具改写为硬盘加密工具 pqdiskcrypt**：核心密码学构造原样保留并新增“卷模式”，前三轮的评审结论与测试全部继续有效。前三轮的说明保留如下。
>
> **本文档含三轮工作：** 第一轮（一～五节）是对原实现的复核 + 一道不改格式的启动自检闸门；第二轮（**六节**）新增了**可选的后量子发件人认证（ML-DSA-87 数字签名）**；第三轮（**七节**）是一次**独立复审**：密码学构造再次确认无需改动，工作重心转到"密码学之外"的真实薄弱点——秘密在浏览器里的暴露面、人选口令、由文件控制的资源消耗、自检闸门的一个绕过路径、以及 Web 平台层的注入面——并首次为浏览器接线层建立了可在 Node 下复现的端到端冒烟测试。第三轮**不改文件格式、不改密钥格式**，旧文件 / 旧密钥 / 旧版工具全部照常互通。

## 一句话结论

这份工具的密码学构造**本身已经很扎实、且偏保守正确**，不存在需要"修补"的漏洞。第一轮我没有重写任何加密逻辑，只**叠加了一道经过验证、不触碰文件格式的运行期防护**。第二轮新增的发件人签名是一项**能力增强**而非补漏：它是可选项、默认不开启（保留可否认性），新增的签名用 **Sign-then-Encrypt + 收件人绑定**构造，签名值置于密文内部（不泄露发件人身份），且与既有未签名文件、旧版工具**双向兼容**。第三轮（七节）是独立复审：密码学再次确认无需改动，修复了自检闸门的一个绕过路径、私钥明文被渲染进页面、口令无任何门禁、文件可控的 KDF 参数可让浏览器卡死等"密码学之外"的真实薄弱点，并把 CSP 收紧到不含任何 `unsafe-inline`、为接线层首次建立了可复现的端到端测试。

## 一、我对现有实现的复核结论（均确认无误）

用真实的 ML-KEM-1024（noble）+ 真实的 Argon2id（hash-wasm）+ Node 原生 WebCrypto，对全部路径做了端到端验证（空文件、跨块边界、多块、篡改、错误口令/私钥、私钥容器、严格校验），**23 项全部通过**。具体确认：

- **混合 KEM 组合器**采用 X-Wing 风格的"随机预言机一次性哈希"：`SHA-512(域标签 ‖ ss_mlkem ‖ ss_x25519 ‖ mlkem_ct ‖ mlkem_pk ‖ eph_pk ‖ recip_pk ‖ salt)`。两份共享密钥与全部相关公开值一并绑定，只要任一 KEM 不被攻破即安全；同时显式绑定收件人静态公钥，杜绝重封装/密钥混淆类攻击。设计注释里"不用 HKDF 以回避对偶 PRF 假设"的论证是正确的。
- **密钥承诺（committing AEAD）**：64 字节哈希输出前 32 作 AES 密钥、后 32 作承诺值，解密前**常数时间**比对。这从根本上消除了 AES-GCM 的分区谕示/多密钥伪造（Invisible Salamanders）一类隐患，承诺值同时被纳入 GCM 的 AAD，双重保险。
- **流式 AEAD**：64 KiB 分块，nonce = 大端计数器 ‖ 末块标记，整个文件头作 AAD。截断/扩展/重排都会令认证失败——逐项验证均按预期拒绝。
- **口令模式**：Argon2id 256 MiB / t=4 / p=4，参数随头保存；解密侧对参数设了上限（≤2 GiB 等），可防恶意文件触发内存耗尽。
- **私钥落盘加密**：Argon2id + AES-256-GCM + 承诺，错误口令快速明确失败。
- **CSP 极严**：`default-src 'none'; connect-src 'none'; script-src 'self' 'wasm-unsafe-eval'; …`。**这一点很关键**——即便某个 vendor 库被恶意篡改想偷密钥，也没有任何外联通道可供其外泄。
- **Argon2id 默认值（256 MiB）是正确取舍**，不建议上调：再高会显著增加移动端/浏览器 OOM 风险，反而损害可用性（=安全性的一部分）。这属于"不动才是最安全"的情形。

## 二、我实际做的加固：启动自检闸门（唯一改动）

**问题**：原版在让用户用"刚加载进来的算法库"加密真实数据之前，**没有任何行为校验**。万一某个 `vendor/*.js` 文件损坏、构建出错、或被掉包成错误参数集（例如 ML-KEM-768 冒充 1024），加密可能"看似成功、实则产出无法解开或弱密钥的文件"——而用户毫不知情。

**改动**：在加密核心新增 `selfTest()`，并在浏览器启动时（两个算法库都就绪后）自动运行一次。它用一段极小载荷把整条流水线跑通：

1. RNG 不是常量、不全零；
2. ML-KEM **参数集正确**（公/私钥/密文长度严格等于 FIPS 203 ML-KEM-1024）且 KEM 往返自洽；
3. 混合模式 / 口令模式 / 私钥容器三条路径都能加解密往返；
4. 篡改密文、错误口令都被正确拒绝（即承诺 + GCM 确实在生效）。

**任一步失败 → 立即禁用密钥生成/加密/解密**，并提示用户下载到本地用桌面浏览器打开。三个动作入口都加了独立守卫，即便按钮被重新启用也拦得住。

**特性**：
- **格式中立**：已交叉验证——原版加密的文件改版能解、改版加密的文件原版能解，双向、各模式一致。旧文件、对方用旧版加密的文件都照常能解。
- **开销极低**：自检里的口令/容器环节用极小 Argon2 参数（仅验证流水线，**不**代表实际加密强度），整轮约 0.1 秒，**不会**在启动时占用 256 MiB。
- **零回归**：改动后端到端 23 项仍全绿。
- **实测有效**：把库换成 ML-KEM-768 冒充，自检确实当场拦下。

改动范围：`app.js` 净增约 88 行，全部为叠加的防御代码 + 三处入口守卫 + 启动接线；另顺手把两句早已过时的诊断日志（"CDN 被拦截"）改为准确描述本地模块加载失败。**没有一行现有加解密逻辑被改动。**

## 三、自检的诚实边界

自检只能发现**"行为不正确"**（损坏 / 错配参数集 / 构建出错），**无法发现"行为正确但暗中泄密"的恶意库**。后者由上面提到的严格 CSP（全程禁止任何外联）来兜底：恶意库即使拿到密钥也无处可送。两者配合，覆盖了"库被动坏掉"和"库主动作恶"两类情形。

## 四、我**刻意没做**的事（及原因）

- **不重写/不改密码学构造、不改文件格式**：现有构造已可证明安全且保守，改动只会增加风险、且破坏与旧文件的互通。
- **不给 vendor 库加 SRI/哈希校验**：`import()` 无法用 SRI 属性；而要 `fetch` 库文件来自行哈希又会被 `connect-src 'none'` 挡住——为此放宽 CSP 是**更不安全**的。现有严格 CSP 已是更好的兜底。
- **不上调 Argon2id 参数**：见上，会损害移动端可用性。

这些要么超出"加固现有方案"的范围、要么无法在当前约束下安全落地，列出供参考：

1. **发件人认证 / 不可否认性**：~~当前方案提供机密性 + 完整性，但不认证发件人~~ → **本轮已实现（见第六节）**。当你上传了 `ml-dsa.js` 后，我把 ML-DSA-87 签名作为**可选**能力接入了文件格式。仍保留"默认不签名"以兼顾**可否认性**——是否签名取决于你的威胁模型。

## 六、第二轮升级：可选的后量子发件人认证（ML-DSA-87）

### 6.1 解决什么问题
原方案是**匿名加密**：任何拿到你 `.pub` 的人都能给你发一份"合法"的加密文件，你无法在密码学上确认它**究竟是谁发的**。本轮新增**可选**的发件人数字签名，让发件人能证明"此文件确由我发出、且确实发给你"。

### 6.2 算法与构造（关键设计决策）
- **算法：ML-DSA-87**（FIPS-204，安全等级 5），与现有 ML-KEM-1024 同级；运行期以注入库 `lengths` 严格校验（pk 2592 / sk 4896 / sig 4627）。
- **构造：Sign-then-Encrypt（先签名后加密）+ 收件人绑定**。
  - **签名值放进密文内部**（封套），对外**不泄露发件人身份**——契合隐私工具定位。
  - 被签名的消息绑定：`域标签 ‖ 收件人X25519公钥 ‖ 收件人ML-KEM公钥 ‖ 发件人ML-DSA公钥 ‖ SHA-512(明文)`。
  - **绑定收件人** → 抵抗"偷偷转发/改投"（surreptitious forwarding）：恶意收件人无法把你的签名重投给第三方冒充成"发给对方"——第三方验签时用自己的公钥重算消息，必然失败。
  - **绑定明文哈希** → 证明对"这份内容"的作者身份；签名开销与文件大小无关（明文先用 WebCrypto SHA-512 压成 64 字节，**不引入新核心依赖**）。
- **与机密性层正交**：封套先被既有"密钥承诺 + 流式 GCM"整体认证，ML-DSA 验签是在**已认证明文之上**再加的一道发件人证明。**验签失败一律"失败关闭"**（抛错拒绝，绝不把明文当"未签名"静默返回）。

### 6.3 格式与兼容性（务必知悉）
- 新增**模式字节 `MODE_HYBRID_SIGNED = 3`**；**文件版本字节仍为 2**，未签名文件与旧格式**逐字节同构**（mode 仍为 1）。
- 身份密钥升级为 v3：在 `.pub`/`.key` 中**追加** `mldsa_pub`/`mldsa_secret`。**ML-DSA 字段在校验中是可选的**：
  - 旧版 v2 密钥**仍可**接收、解密、**验证他人签名**、发送未签名文件；**只有"作为签名者"才需要含签名身份的 v3 新密钥**（验签用的是发件人内嵌的公钥，收件人自己无需签名密钥）。
- **对拍已验证**（见 6.5）：新代码 ↔ 旧代码未签名/口令文件双向互通；新 v3 密钥的未签名文件旧代码也能解；**旧代码遇到签名文件(mode=3) 会安全拒绝**（"未知模式"），不会误处理。

### 6.4 信任模型（诚实边界）
- 验签通过后展示**发件人签名指纹**（SHA-256(独立域标签 ‖ ML-DSA公钥) 截断 16 字节）。这证明"签名在密码学上有效且绑定了你这个收件人"，但**指纹对应谁**仍需你通过**另一渠道**与发件人核对（TOFU / 类似 SSH 指纹）——工具不内置 PKI / 信任根。
- **签名 = 放弃可否认性**：一旦签名，你便无法再否认发过此文件。故默认**不签名**，UI 中明确标注此取舍。
- 自检/CSP 边界同第三节：`connect-src 'none'` 同样兜底新引入的 `ml-dsa.js`——即便该库被恶意篡改，也无外联通道可外泄密钥。

### 6.5 改动范围与验证
- **未触碰任何已验证核心**：KEM 组合器、密钥承诺、流式 GCM、Argon2、私钥容器、`encryptHybrid`/`buildHeaderHybrid` 均**逐字未改**；签名走**新增**函数（`encryptHybridSigned` 等），宁可少量重复也不重构共享核心。
- **vendoring**：`ml-dsa.js` 为 npm 源码形式，已将其 4 行 import 改写指向既有 esm.sh 扁平化 vendor 文件，并为它唯一缺失的依赖 `abool` 提供了忠实小垫片（`_curves_utils_shim.js`；该函数仅用于校验我们从不设置的 `externalMu` 选项，实际从不触发）。**库的算法主体一字未改。**
- 启动自检新增 ML-DSA 分支：参数集长度、签名往返、篡改签名拒绝、**端到端签名加解密往返**、篡改密文拒绝——任一失败同样禁用全部加解密。
- 端到端验证脚本扩充至 **49 项全绿**，新增覆盖：签名往返（各尺寸）、发件人指纹/公钥识别、篡改密文/截断拒绝、无签名身份密钥拒签、**偷偷转发抵抗**（给 R 的签名重投给 V 被拒、同封套发回 R 本人通过），以及与升级前 `app.js` 的**向后兼容对拍**。

## 七、第三轮升级：收窄"密码学之外"的暴露面（独立复审）

### 7.1 复审结论
我从头重读了全部核心（组合器、承诺、流式 GCM、口令 / 容器路径、签名封套与收件人绑定、自检）与两个 vendor 入口，并在真实库上重跑了 49 项用例。**前两轮的密码学判断成立**：构造保守正确，没有需要修补的漏洞；ML-DSA 默认走 hedged（随机化）签名；hash-wasm 用内嵌字节 `WebAssembly.instantiate`，不依赖网络；vendor 里没有任何 DOM / eval 注入点（`fft.js` 里的 `eval` 是多项式求值方法名）。因此第三轮**不重写任何密码学逻辑，不改文件 / 密钥格式**。

真正有改进空间的，是下面这些"密码学以外"的地方——它们决定了一份数学上正确的密文在**真实使用**中会不会被绕过。

### 7.2 发现并修复的问题

**(1) 自检闸门存在绕过路径（第二轮机制的逻辑漏洞）。** 原实现只在启动时"三库同时就绪"后跑一次自检；若某个库启动时**暂时**加载失败（例如首次打开时被拦截、之后重试成功），用户点击按钮时 `ensureNoble()` 会按需重新加载并**直接放行**，自检从未执行。同时"生成密钥"入口只确保了 ML-KEM 载入，未确保 ML-DSA 载入，会以 TypeError 失败。
→ 现在所有入口（生成 / 加密 / 解密 / 私钥落盘加密）统一经过 `ensureReady()`：**三库全部载入 → 自检恰好通过一次** 才放行；自检失败是永久状态（库被判定损坏 / 掉包），库加载失败则允许下次点击重试。这把"自检"从"启动时的一次检查"变成了真正的**门禁**。

**(2) 明文私钥被原样渲染进 DOM。** "密钥"页的私钥预览框（`keyPeek`）把 `x25519_priv / mlkem_secret / mldsa_secret` 完整写进了页面——截屏、屏幕共享、旁观、以及任何能读页面的扩展都能拿走。
→ 预览改为**结构脱敏**：秘密字段一律替换为 `<字段名 · N 字节 · 已隐藏>` 占位符，只有公钥字段原样展示；完整私钥只存在于下载的 `.key` 文件中。冒烟测试逐字段验证秘密区段的任何子串都不出现在页面里（注意 ML-KEM 私钥内嵌公钥、ML-DSA 私钥以公开种子 ρ 开头，这些片段本就是公开的，测试只检查真正的秘密区段）。

**(3) 口令是口令模式与私钥容器的唯一安全来源，却没有任何门禁。** Argon2id 256 MiB 只能把"每次猜测"变贵，挡不住 `password` / `19900101` 这类几秒内就能猜中的口令。
→ 新增依赖零、可离线测试的 `passwordStrength()`：**硬性拦截**空口令、少于 8 个字符、以及公开泄露榜单头部 + 中文用户高频的极常见口令（`123456`、`woaini1314`、`5201314`…，含去符号匹配如 `P@ssw0rd`）；**启发式估算**（按码点计数、字符集熵、重复 / 单调序列与键盘走位扣分、字符种类过少封顶）给出"很弱 / 弱 / 一般 / 较强 / 强"，很弱与弱需用户明确确认才能继续，并把选择写进日志；对纯数字、纯小写短口令、首尾空白、全角字符（输入法误切）给出提示。强度条随输入实时更新。**估算只是启发式**——它能挡住明显糟糕的口令，不能证明一个口令是好的，页脚已如实说明。

**(4) 同一口令在不同设备上可能是不同字节 → 自己锁死自己。** 带音标 / 组合字符的口令（é、ü、越南语等）在 macOS 与 Windows、不同输入法下可能分别以 NFD / NFC 形式输入，Argon2 看到的是不同字节，文件在另一台机器上就打不开。
→ 加密 / 私钥落盘时统一 **Unicode NFC 规范化**（RFC 8265 的做法；纯 ASCII 与中文不受影响，字节不变）。解密 / 解锁时先按 NFC 尝试，若核心明确返回"口令错误"（新增 `err.code === "BAD_PASSWORD"`，不再靠匹配中文文案）且原串与规范化串不同，再以原始字节**重试一次**——兼容早期版本创建的文件；篡改 / 损坏类错误不做重试。冒烟测试用 NFD 输入的口令做了"新文件按 NFC 加密 / 旧文件回退可解"双向验证。

**(5) 由文件控制的 Argon2 参数可以让受害者的浏览器卡死。** `.pqfc` 文件头与 `.key` 容器里的 `t / m / p` 由文件而非用户决定；核心的上限（2 GiB / t≤64）只是"不至于无限"，一份恶意文件仍可让解密方分配 GiB 级内存、跑上几分钟甚至崩掉标签页——而用户在点击前一无所知。
→ 载入文件时即在日志中显示实际参数；当内存或时间**超过本工具默认值 2 倍**（或并行度超过 2 倍）时，解密 / 解锁前弹出确认，说明这些参数来自文件本身、可能是恶意的；取消则**不执行任何 KDF**。默认参数与 2 倍以内的合理设置不会打扰用户。核心上限保持不变（不动经验证的常量）。

**(6) Web 平台层：去掉最后的注入面。**
- `sr.innerHTML = "…" + res.signerFingerprint + …`：指纹是 SHA-256 的十六进制，当前不可注入，但这是页面里唯一一处"字符串 → HTML"。现改为 DOM API 拼装（`setRich()`），全页**不再存在任何 innerHTML / eval / new Function / document.write**。
- CSP 新增 **`require-trusted-types-for 'script'`**：支持该指令的浏览器会在运行期禁止一切字符串式 DOM 注入 sink，即便未来有人改坏了代码；不支持的浏览器安全忽略。
- 内联 `<style>` 与 4 处 `style=""` 属性外置为 `app.css` / class，CSP 的 `style-src` 从 `'self' 'unsafe-inline'` 收紧为 **`'self'`**。现在整个 CSP 里**没有任何 `unsafe-inline` / `unsafe-eval`**，仅保留 WASM 必需的 `'wasm-unsafe-eval'`。选择外置文件而不是给内联样式加哈希，是因为哈希会在你下次改一行 CSS 时让整页失去样式且难以排查——脆弱的加固会被人绕开或拆掉。
- 明文导出私钥前增加一次明确确认（此前一键即出）。

**(7) "清除敏感状态"按钮。** 生成密钥后，私钥对象 `lastKeys`、载入的明文 `.key`、已解封的容器、各口令输入框会一直留在页面内存里直到关闭标签页；在共用电脑上这就是暴露窗口。新按钮清空全部口令输入与预览、丢弃所有密钥 / 文件引用、尽力清零已读入的密文缓冲区，然后**重新载入页面**（丢弃整个 JS 领域）。按钮提示与日志都如实写明：JS 无法保证物理抹除内存，敏感场景请直接关闭标签页。

**(8) 核心两处微加固（不改格式）。**
- `b64decode` 补上**规范性检查**：末尾残余位必须为 0，否则 `QQ==` 与 `QR==` 会解出同一密钥（第一轮注释里声称已消除的"可塑性"其实只做了一半）。本工具与所有标准编码器只产出规范编码，现有密钥 / 容器不受影响，49 项回归 + 0..70 字节随机往返验证通过。
- `x25519GenerateRaw` 不再盲取 PKCS#8 导出的"末 32 字节"，而是严格断言 RFC 8410 v0 结构（48 字节、16 字节前缀逐字比对）——若某实现导出带公钥附件的 v2 结构，末 32 字节会是**公钥**。此前自检的往返测试也能间接发现该情况，现在失败原因是明确的。

**(9) 部署 / 文档层的错误信息。** 原横幅仍在说"预览沙箱拦截了外部 CDN"（早已本地化）并建议"用 Chrome 直接打开"——Chrome 出于同源策略**不允许从 file:// 载入 ES 模块**，按这个建议操作只会再次失败。现改为：用 Firefox 直接打开，或在目录内起一个本地 HTTP 服务后用任意浏览器访问。另修正 `fonts/fonts.css` 引用的字体文件名与磁盘文件大小写不一致的问题（在 Linux 等区分大小写的文件系统上字体不会加载）。

### 7.3 验证方式（新增）
- `_verify/verify.mjs` 从 49 项扩到 **132 项**：新增核心微加固用例（规范 Base64、PKCS#8 断言、错误码语义——篡改密文的失败**不**带 `BAD_PASSWORD`，因此 UI 不会对其做口令回退重试）、口令卫生纯函数用例（含中文、NFD/NFC、全角、纯数字、常见榜单）、KDF 成本判定、以及一组**静态检查**：CSP 各指令、页面无内联 script/style/事件属性、`app.js` 无 innerHTML / eval / 浏览器存储 / 网络 API、只 import 本地 vendor、引用的 44 个元素 id 全部存在、字体文件引用存在、vendor 无注入点。
- **`_verify/ui-smoke.mjs` + `_verify/minidom.mjs`（首次为接线层建立测试）**：一个极简 DOM 仿真解析真实 `index.html`，把 `window / document` 挂到全局后 import 真实 `app.js`，在真实 ML-KEM / ML-DSA / Argon2id 上按用户操作顺序点按钮：预载 + 自检、生成密钥 + 预览脱敏、口令门禁（拦截 / 确认 / 取消）、口令模式加解密（NFC）、旧 NFD 文件回退、用受口令保护的私钥签名与解密验签、恶意 KDF 参数确认与取消、清除按钮。共 30 项，随 `verify.mjs` 自动运行。它不是浏览器，验证不了 CSP / Trusted Types 的运行期行为（那部分靠静态检查 + 人工在 Firefox / Chrome 里打开一次确认无控制台报错），但把此前完全没有测试的按钮逻辑、状态机与错误路径全部盖住了。

### 7.4 刻意没做的事（及原因）
- **不给 vendor 模块加 import-map `integrity` 哈希。** 技术上可行（新式 import map 支持 integrity，且能覆盖动态 `import()`），但本工具从本地目录运行：能改 `vendor/*.js` 的攻击者同样能改 `index.html` 里的哈希，它只防"部分篡改"这种边缘情形；代价是任何一次 vendor 文件变动（哪怕一个换行）都让整页失效。收益小、脆性大，维持第一轮的判断：`connect-src 'none'` 才是对恶意库的真正兜底。
- **不动 Argon2 上限常量、不上调默认参数**：理由同前两轮；第 (5) 项的确认提示已把"文件控制的高成本参数"从静默变为知情。
- **不做私钥文件"公钥 ↔ 私钥一致性"校验**：`.key` 内嵌的公钥若被篡改，后果只是承诺值不匹配、失败关闭（或签名无法被收件人验证），没有泄露；加校验会触碰经验证的 `validateKeyObj`，收益是更友好的报错而非安全性。
- **不缩短 / 不改指纹格式**：128 位截断对"第二原像"（伪造与某公钥同指纹的密钥）是 2^128，够用；碰撞攻击需要攻击者同时控制两把密钥，对带外核对无意义。改格式会让用户已记录的指纹失效。
- **不做前向保密、不做填充隐藏文件大小**：静态文件加密的固有属性，与前两轮结论一致。

### 7.5 诚实边界
- 口令强度估算是启发式，不是 zxcvbn 级别的字典 / 模式分析；它的目标是拦住"瞬间可破"的口令并让用户对弱口令做出知情选择。
- 私钥预览脱敏与清除按钮缩小的是**页面内**的暴露面；已加载到 JS 内存里的秘密（包括 Base64 字符串）无法被可靠清零，能读进程内存的攻击者不在本工具的防护范围内。
- Trusted Types 与 `style-src 'self'` 在不支持的旧浏览器上会被忽略，此时退回到"代码本身没有注入点"这一层保护。
- `ensureReady()` 消除的是"绕过自检"，自检本身的边界不变（见第三节）：只能发现行为不正确的库，发现不了行为正确但暗中泄密的库。

## 八、第四轮：改写为硬盘加密工具（pqdiskcrypt）

### 8.1 做成了什么
原工具一次只加密一个文件、结果靠“下载”落地。第四轮把它改写成**对整块移动硬盘 / U 盘 / 任意目录树原地逐文件加密**的工具：用 File System Access API 拿到目录的读写句柄，遍历其中每个文件，流式写出密文、重新读取校验、再删除原文件；解密反向进行。代码分成三层：`pqcore.js`（密码学核心，前三轮代码原样搬入 + 卷模式）、`pqvolume.js`（目录树引擎，只依赖目录句柄的 6 个方法，可在 Node 内存文件系统上完整测试）、`app.js`（界面接线）。

### 8.2 密码学设计（新增“卷模式”，文件格式版本字节仍为 2，新模式字节 4）
- **卷主密钥 VMK**：每个卷一把随机 32 字节密钥，**从不直接落盘**，只以“密钥槽”形式存在于根目录的卷头 `.pqvolume`（JSON）中。这是 LUKS / BitLocker 的密钥槽思路：
  - **口令槽**：`Argon2id(口令, salt)` → `SHA-512("pqdisk:v1:slot-kdf:argon2id" ‖ 主密钥)` → {包裹密钥 32B, 承诺值 32B}；
  - **公钥槽**：与 v2 单文件完全相同的 X-Wing 式 X25519 + ML-KEM-1024 组合器，但用独立域标签 `pqdisk:v1:slot-kem:…`（`hybridDerive` 只是多了一个默认值等于旧标签的 `label` 参数，v2 路径字节行为不变，回归测试证实）；
  - 包裹：`AES-256-GCM(包裹密钥, 随机 nonce, AAD = "pqdisk:v1:slot-wrap:…" ‖ 卷 ID ‖ 槽类型字节)` 加密 VMK。AAD 绑定卷 ID 与槽类型，杜绝把槽移植到别的卷头、或把口令槽伪装成公钥槽；每个槽都带承诺值，错误口令 / 不匹配私钥在做 GCM 之前就能常数时间明确失败。
  - 好处：**更换口令、追加公钥、吊销某把钥匙只需改写卷头**，无需重新加密整块硬盘；Argon2id（256 MiB）只在解锁时跑一次，成千上万个文件的逐文件加密只有哈希 + AES 开销。
- **逐文件密钥**：`SHA-512("pqdisk:v1:file-key:vmk" ‖ VMK ‖ 卷 ID ‖ 文件 salt(16B 随机))` → {文件密钥, 承诺值}。文件头 = `MAGIC ‖ 0x02 ‖ 0x04 ‖ 卷 ID(16) ‖ salt(16) ‖ 承诺值(32)`，定长 74 字节；正文与 v2 逐字节同构（64 KiB 分块、nonce = 计数器 ‖ 末块标记、头作 AAD）。文件头里明文写卷 ID 是有意的：不用密钥就能判断一个 `.pqfc` 属于哪个卷（扫描 / 跳过 / 拒绝二次加密都靠它），卷 ID 本身不是秘密。
- **真正的流式接口**：`encryptStreamTo / decryptStreamTo` 接 `ReadableStream`，重切块器扣留一块以判定末块，`ByteReader` 按需拉取；大文件不再整体读入内存。与整块接口线格式相同，测试里两两交叉往返（0 / 1 / 64K±1 / 多块）验证。
- **旧版工具遇到 mode=4 会以“未知模式”安全拒绝**，卷模式解密也拒绝单文件模式的文件（`NOT_VOLUME_FILE`），两者互不误处理（已测）。

### 8.3 引擎的安全次序（每个文件）
写出密文 → `close()` →（默认开启）重新读取密文、完整校验每块认证标签且长度一致 → **才删除原文件**。任一步失败：删除写了一半的输出，原文件原样保留，记入错误列表，继续处理其它文件；`NotAllowedError / SecurityError` 视为致命立即中止。取消在块与块之间检查，同样丢弃半成品、保留原文件；已完成的文件保持加密，再运行一次即可续跑（内存文件系统上做了取消 / 续跑 / 写入翻转一字节 / 磁盘满 的故障注入测试）。

几条刻意的规则：
- **明文优先，不做“猜测式续传”**：目录里若存在明文，本次一律重新加密并覆盖同名旧密文；绝不因为“同名密文已存在”就删掉明文——那可能删掉一份改动过的新文件。“已加密”的判断只基于文件头里的卷 ID。
- **绝不二次加密**：属于其它卷或单文件模式的 `.pqfc` 一律跳过并保留（最常见的情形是误选了某个加密卷的子目录）。输出名若已被占用，只允许覆盖“本卷自己的旧密文”，任何其它东西不覆盖。
- **解密不覆盖同名明文**：目标已存在则跳过并保留密文；卷头只在**零错误、零警告**时才移除，否则保留以便重试。
- **不使用 `move()` / 重命名**：Chrome 对本地目录尚未稳定支持；所有写入只经 `createWritable()`（Chrome 会写临时文件再原子替换，所以中途失败不会破坏已有文件）。代价是加密过程中硬盘需有“最大单文件”大小的可用空间。
- **隐藏文件名模式**（新建卷时可选）：文件与目录一律改名为 16 位十六进制随机 ID，每个目录放一份加密清单 `.pqdir`（本身就是卷文件，明文 JSON 内含本目录 ID 用于防调换）。清单在处理该目录之前就落盘、每次运行重写并清理孤儿条目；清单丢失时内容仍能救回（按 ID 命名并告警）。外来 `.pqfc` 因不迁移，其所在目录名会保留（日志会说明）。
- **卷头备份**：新建卷时自动下载 `pqdisk-<卷ID>.pqvolume`；解密页可在卷头丢失时载入备份写回；卷管理页可查看 / 增删密钥槽 / 下载 / 写回（写回前必须先能解锁，防止把不相干的备份写到别的卷上）。

### 8.4 威胁模型与诚实边界（请如实告知用户）
- 这是**文件级**加密，不是 BitLocker / VeraCrypt / LUKS 那样的扇区级全盘加密：不能加密系统盘、正在被占用的文件；文件**大小、数量、目录深度、修改时间**等元数据仍可见（隐藏文件名模式只遮住名字）；不做填充、不做前向保密——与前三轮对静态文件加密的结论一致。
- **被删除的原文件在磁盘上可能仍可被恢复**（机械盘 / SSD 皆然，且 Chrome 的“临时文件 + 替换”写法让“覆写原文件”这类做法无效，所以没有提供“安全删除”选项以免给出虚假安全感）。若硬盘之前长期存放过明文，应对整盘安全擦除或改用全盘加密；最稳妥的是先加密再往盘里放文件。页面显著位置写明了这一点。
- 卷头 `.pqvolume` 丢失 = 全卷无法解密（和 LUKS 头一样）。因此自动下载备份并在多处提示。
- 密钥槽被删除只对之后的访问有效：持有旧卷头 + 密文拷贝的人仍能解开那份拷贝（所有密钥槽方案的共同性质，页面已说明）。
- 仅 Chrome / Edge 桌面版可用（File System Access API）；且必须经 `http://localhost` 打开（附 `serve.py`，只监听 127.0.0.1，并下发 `X-Frame-Options: DENY` / `frame-ancestors 'none'` / `Cache-Control: no-store`）。Argon2id 仍在主线程运行，解锁时页面会卡住数秒。
- 浏览器无法可靠抹除内存中的 VMK；“清除敏感状态”按钮会尽力清零并重载页面，敏感场景请直接关闭标签页。

### 8.5 验证（第四轮新增）
- `pqcore.js` 的 `selfTest()` 新增卷模式分支（密钥槽往返、错误口令 / 错误私钥拒绝、流式 ↔ 整块互通、篡改 / 截断 / 外卷 / 错误主密钥拒绝），启动时照旧作为门禁。
- `_verify/verify.mjs`：新增卷模式核心用例（槽字段 / 承诺 / 归属 / 74 字节头 / 追加伪造块 / ByteReader 语义 / 旧版拒绝 mode=4 …），静态检查扩到三个模块与 `serve.py`。
- `_verify/volume-test.mjs` + `_verify/fakefs.mjs`：内存版 File System Access API（贴近 Chrome 语义：写临时缓冲、close 时替换、TypeMismatchError / NotFoundError / InvalidModificationError、故障注入、不规则分片读取）上跑整盘加解密：普通 / 隐藏两种模式全树往返、重复运行、追加文件、公钥槽、密钥槽增删、取消与续跑、写入损坏被校验拦下、磁盘满、篡改 / 外来 `.pqfc` / 同名冲突、清单丢失救回、只读权限致命中止等。
- `_verify/ui-smoke.mjs`：仿真 `showDirectoryPicker` 返回内存目录，按用户操作顺序驱动真实 `app.js`：扫描、口令门禁、口令 + 公钥双槽建卷、隐藏文件名、自动下载卷头备份、已有卷追加文件（错误口令拒绝）、用受口令保护的私钥解锁公钥槽解密、卷头丢失后载入备份、卷管理（解锁 → 追加口令槽 / 公钥槽 → 删除旧槽 → 旧口令失效）、写回卷头、半途取消、清除按钮。

## 九、第五轮：改写为不需要浏览器的单文件桌面程序（pqdiskcrypt.py）

### 9.1 做成了什么
浏览器版依赖 Chrome / Edge 的 File System Access 接口，且必须经 `http://localhost` 打开（附带 `serve.py`）。第五轮把整套工具改写成**一个 Python 文件** `pqdiskcrypt.py`：tkinter 图形界面（Python 自带）、直接读写真实文件系统、"下载"改为另存对话框；不再有本地服务器、CSP、浏览器沙箱与 Web Crypto。**磁盘格式一个字节都没有改**：`.pqvolume` / `.pqfc` / `.pqdir` / `.pub` / `.key` 与浏览器版互通（9.4 有双向证明）。文件内部仍分三层，与 JS 版一一对应：纯 Python 后量子原语 → 密码学核心（`PQCrypto`，对应 `pqcore.js`）→ 目录树引擎（`VolumeFS`，对应 `pqvolume.js`）→ 界面（`App`，对应 `app.js`）。

### 9.2 算法库的来源（与浏览器版的差异）
| 原语 | 浏览器版 | 桌面版 |
|---|---|---|
| AES-256-GCM / SHA-512 / SHA-256 / X25519 | Web Crypto（浏览器原生） | `cryptography`（OpenSSL） |
| Argon2id | hash-wasm | `cryptography ≥ 44`（OpenSSL ≥ 3.2 的 Argon2），后备 `argon2-cffi`；启动时用 8 KiB 参数探测可用性 |
| ML-KEM-1024 / ML-DSA-87 | `@noble/post-quantum` 0.5.4 | **本文件内置的纯 Python 实现**（FIPS 203 / 204 终稿，含 ML-DSA 的上下文串 `0x00‖len‖ctx‖M` 与 hedged 签名） |

选择纯 Python 实现而不是引入第三方 PQC 包，是为了保持"单文件、只依赖一个常见库"；代价是必须证明它与原实现**逐字节一致**，这由 `_verify/vectors.json` 完成：用冻结的 noble 从固定种子生成密钥、用固定 `m` 封装、解封、篡改密文触发隐式拒绝、确定性签名（`extraEntropy:false`）、带上下文串的签名、hedged 签名；Python 端对每一项都做字节相等比对（不是"能互通"而是"完全相同"），随机路径再做双向互操作（Python 封装 / 签名 → JS 解封 / 验签，反之亦然）。Argon2id 同样与 hash-wasm 的输出逐字节比对。

诚实边界：纯 Python 的 ML-KEM / ML-DSA **不是常数时间**（Python 大整数与列表运算天然依赖数据），与 noble "不防侧信道" 的声明处于同一级别；两者都未经独立审计。本工具的威胁模型是离线的静态数据加密，攻击者拿到的是硬盘而不是运行中的进程，这与第一轮以来的结论一致。

### 9.3 引擎落到真实文件系统后的安全次序（每个文件）
- 写到同目录的临时文件 `.pqdisk.tmp.<随机>` → `flush` + `fsync` → （默认开启）重新读取临时文件并完整校验每块认证标签与长度 → `os.replace` 原子替换到目标名 → **才删除原文件**。任一步失败：删除临时文件，原文件原样保留，记入错误列表，继续处理其它文件。比浏览器版多了显式 `fsync` 与原子替换（Chrome 只是隐式地这样做）。
- 中断（取消 / 崩溃 / 断电）后残留的 `.pqdisk.tmp.*` 在下次运行时自动清理并记入日志；扫描时把它们单独计数，绝不当作明文去加密。
- 符号链接 / Windows 联接点 / 设备文件一律跳过且**不进入**（浏览器接口本来拿不到这些），避免顺着链接加密目录树之外的东西。
- 单个文件的权限错误（Windows 上被占用、只读属性）记为该文件的错误而不是致命中止：浏览器版把 `NotAllowedError` 视为致命，是因为它意味着整个目录句柄的权限被收回；桌面版没有这个语义。删除只读文件会先去掉只读位再试一次。
- 卷头与目录清单也经"临时文件 + 原子替换"写入。修改时间：加密时把原文件的 mtime 复制到密文，解密时再复制回明文（浏览器接口做不到）。
- "明文优先、绝不二次加密、解密不覆盖同名明文、卷头只在零错误零警告时移除、密钥槽最少保留一个、写回卷头前必须先能解锁"等规则全部原样保留，并由 Python 测试逐条覆盖。

### 9.5 与浏览器版相比的威胁模型变化
- 程序以用户的完整权限运行，没有浏览器沙箱与 CSP：`pqdiskcrypt.py` 本身和 `cryptography` 包的来源（pip 供应链）成了信任根，启动自检只能发现"行为不正确"的库，发现不了"行为正确但暗中泄密"的库，这一点与第二节的结论相同。
- Python 无法可靠抹除内存（`bytes` 不可变；本程序把卷主密钥放在 `bytearray` 并尽力清零）；"清除敏感状态"按钮只重置界面状态，敏感场景请直接退出程序。
- 好处：Argon2id 与逐文件加解密都在后台线程，界面不卡；可以直接选盘符根目录；没有"必须用 Chrome / localhost"的门槛；不再有任何网络面。

### 9.6 刻意没做的事
- 没有做"安全删除 / 覆写原文件"（理由同 8.4：SSD 与文件系统的写入方式使其给出虚假安全感）。
- 没有引入拖放库（tkinterdnd2）或 PQC 第三方包，以保持单文件、单依赖。
- 没有随包提供编译好的可执行文件（无法在此处为你的平台构建，也不希望你信任一个来路不明的二进制）；README 给了 PyInstaller 一行命令。

### 9.7 第五轮补丁（v5.1）：隐藏文件名卷"解密不了"的根因，以及加密后切换隐藏文件名
用随机目录树做模糊测试（`fuzz`：随机深度 / 重名 / 半途取消续跑 / 事后追加文件，150 轮）后发现一个**真实缺陷，浏览器版的 `pqvolume.js` 同样存在**：

- **解密时"目标已存在则跳过"没有把该目录标记为"未处理干净"**。于是一次全部被跳过的解密（最典型的情形：加密时勾了"保留原文件"做试运行，之后直接解密）会以"零错误、零警告"结束，进而**删除全部 `.pqdir` 目录清单并移除卷头 `.pqvolume`**，而文件仍然是密文。隐藏文件名卷受害最重：清单没了就再也对不回原名，卷头没了（且没保存备份）就再也解不开。这正是"选了隐藏文件名之后解密不了"的成因。
- 修复：跳过的文件计入 `kept`，并令该目录 `clean=false`；清单与卷头只在真正还原了全部文件后才删除；界面明确提示"移走同名文件后再解密一次即可"。回归测试 `test_dry_run_then_decrypt_keeps_manifests_and_header` 与界面冒烟"试运行后解密"覆盖。
- 同时发现的边界：隐藏文件名卷跨多次运行后，可能出现"一个新文件与早已迁走的目录同名"（真实文件系统里同时存在不了，但卷里可以）。原先解密到这里会报"无法创建目标目录"并中断该子树；现在目录改以 `原名 (目录, 原 ID …)` 还原并告警，卷头保留。同名文件的情形沿用"明文优先"规则：新明文覆盖同名旧密文（与浏览器版一致，`test_file_dir_name_conflict_across_runs`）。

**加密后切换隐藏文件名**（用户提出"加密之后改不了"）：逐文件密钥只由 VMK ‖ 卷 ID ‖ 文件 salt 派生，密文与文件名无关，所以隐藏 ↔ 显示只是改名 + 增删目录清单，不碰任何密文。实现上：
- 隐藏方向先把卷头的 `hide_names` 写成 true 再改名；显示方向先做一遍**无副作用的冲突预检**（目标名已被占用即整体拒绝、不改任何东西），改名全部成功后才把 `hide_names` 写成 false。因此无论在哪一步中断，卷都仍能解密：还没改名的文件会以"按 ID 命名"告警的方式得到正确的名字（因为它此时的名字就是原名），已改名的照常。
- 外来 `.pqfc`（其它卷 / 单文件模式）与尚未加密的明文一律不动。
- 测试：显示→隐藏→显示→隐藏链式切换后逐字节密文集合不变、随后解密全树一致；冲突预检不留半点改动；界面冒烟里对真实目录切换两次再解密。

浏览器版的同一缺陷未在本包内修复（本包已不再包含浏览器版）；若你仍要使用浏览器版，请避免"保留原文件"后直接解密，并务必持有卷头备份。

### 9.8 第五轮补丁（v5.2）："两个密文只识别一个 / 该目录里没有属于本卷的加密文件"
用户报告同一目录有两个密文却只识别一个，解密报"该目录里没有属于本卷的加密文件"。这不是识别逻辑出错，而是**目录里混有不同卷的密文**：最常见的来路正是 9.7 的缺陷（卷头被误删后用户再次加密，于是新建了第二个卷，旧密文变成"其它卷"），或者用另一个卷的备份覆盖了本目录的卷头。旧界面只笼统地说"其它来源的 .pqfc 将跳过"，用户无从判断，等本卷那一个解完、卷头移除后，剩下的那个就只剩一句"没有属于本卷的加密文件"。

改动（不涉及密码学）：
- 扫描把 `.pqfc` 分成五类分别报告：本卷、其它卷（**按卷 ID 分组计数，短码与备份文件名 `pqdisk-<卷 ID>.pqvolume` 一致**）、单文件模式、头部不完整（已损坏）、无法读取（被占用 / 无权限，原先是静默跳过），以及只是名字像 `.pqfc` 的普通文件。
- 解密页"载入卷头备份"支持**多卷共存**：目录里已有别的卷的卷头时，备份只在本次解密中使用、不写回不覆盖（引擎新增 `remove_header` 参数，用备份解密时不动目录里的卷头），解完自动切回目录卷头；没有卷头或卷头损坏（JSON 无效）时才写回 / 覆盖，并显示目录里有多少密文属于这份备份。
- "没有属于本卷的加密文件"改为指出真正的原因（属于哪个卷、需要哪份备份、还是文件无法读取）。
- 加密页遇到损坏的卷头一律停用加密，遇到其它卷的密文会在确认框里提醒"你将新建一个卷，旧密文只能用它们各自的备份解密"，避免继续制造混卷。
- 验证：引擎测试 `test_scan_reports_foreign_volumes_damaged_and_unreadable`；界面冒烟新增"旧卷头丢失后又新建卷 → 用旧卷备份解出旧文件（目录卷头不动）→ 再解新卷"与"卷头损坏 → 加密页拒绝、解密页用备份覆盖后解密"两条完整流程。

### 9.9 第五轮补丁（v5.3）：诊断能力、单文件页
用户反馈"还是不行"而没有报错文本，此前的判断都基于猜测。为终止猜测，这一版把"看得见"放在首位：
- **诊断报告**（解密页）：按内容逐个检查目录里每个文件（不看扩展名），分成本卷密文、本卷密文但扩展名不是 .pqfc（被改名）、其它卷密文（列出卷 ID）、单文件模式密文（v/模式）、损坏、无法读取、目录清单、残留临时文件、普通文件、系统目录 / 链接（跳过）；写到主目录 `pqdiskcrypt-diag.txt`，只含路径 / 大小 / 分类。发现被改名的本卷密文时提议补回 .pqfc 后缀（`fix_extensions`）。
- **运行日志落盘**：界面日志同步追加到主目录 `pqdiskcrypt.log`；后台线程与 Tk 回调里的未捕获异常连同 traceback 写入同一文件并在界面提示（`report_callback_exception`）。日志从不包含口令、密钥或明文。
- **"没有属于本卷的加密文件"按原因细分**：其它卷（哪个卷、需要哪份备份）/ 单文件模式（去"单文件"页）/ 损坏 / 无法读取 / 可能被改名（用诊断报告）。
- **单文件页**：核心早已完整实现 pqfilecrypt 格式 v2 的三种单文件模式并与 JS 双向对拍，这次接上界面：选中 .pqfc 自动识别模式并切换口令 / 私钥；加密支持口令、收件人公钥、公钥 + 我的签名；解密显示发件人签名指纹。文件整体读入内存（与浏览器版相同）。
- 验证：引擎 `test_diagnose_tree_classifies_by_content`；界面冒烟新增"改名的密文 → 诊断 → 补后缀 → 解密"与"单文件页口令模式 / 签名模式往返、错误口令拒绝"。
